## Builder workflow
- Indonesian UI, no code comments, commit to `main` in small commits, `git pull` before every push.
- A task prompt names a slug. Keep `progress/<slug>-progress.md`: status, a checkbox per phase, and per phase the files changed, commit hash, check result and blockers. On start, resume from the first unfinished phase; never redo a finished one.
- After each phase run only `npx next typegen && npx tsc --noEmit`, append to the progress file, commit, and continue without stopping to report. Stop only at "Wait for my OK" or a failure you cannot fix, after writing the blocker to the progress file.
- Run lint, build or other checks only when the owner asks for them in that task.
- UI work uses `ui-ux-pro-max`; landing and auth pages also use `taste-skill`, redesigns use `redesign-skill` (all in `.claude/skills/`). Ask the owner before visual decisions not settled in the task prompt, and show a mock (screenshots) first for layout changes the owner has not approved.

Aturan teknis
- Semua waktu memakai WIB lewat helper di `lib/format.ts` (`formatJakarta*`, `parseJakartaLocalInput`); jangan pakai `toLocale*String` atau `new Date(datetimeLocal)` langsung.
- Hierarki: organisasi (akun pemilik) -> klub -> pelatih -> anggota. Anggota bisa login (hanya baca, `/member`) setelah diaktifkan admin atau pelatihnya; tidak ada peran orang tua.
- Akun anggota: satu orang satu akun (`accounts`), tiap klub punya profil `member` (`club_profiles.role = 'member'` dengan `account_id`, `club_members.profile_id`). Tabel akun hanya service role. Pindah klub memakai `switchClub`; sesi dengan banyak klub membawa `club_pending` sampai memilih (`requireMemberClub`). RLS peran `member` hanya select baris miliknya (`is_member()`, `current_member_id()`); tidak ada policy tulis. Portal digerbang `requireModule('member_portal')` (`lib/modules.ts`).
- Satu `/login` (username atau email + kata sandi) membaca tabel `accounts` (satu akun universal per orang, satu-satunya tempat kata sandi, lockout, `sessions_valid_after`, `must_change_password`); `organization_users` dan `club_profiles` menautkannya lewat `account_id` (hanya server yang boleh mengisi). Konteks JWT: `ctx` (`personal`/`member`/`org`) dan `account_id`; akun tanpa klub masuk konteks `personal` (`/`, tanpa `club_id`). Buat akun umum di `/signup/account`. Klub hanya bisa menautkan akun anggota yang emailnya terverifikasi atau sudah jadi anggota. Staf, pelatih, dan co-owner masuk lewat undangan berupa tautan (`invitations`, `/i/<token>`, hanya hash token yang disimpan, berlaku 7 hari, sekali pakai); tidak ada lagi kata sandi sementara untuk staf. Reset kata sandi lewat tautan email (`/forgot-password`, `password_resets`, 1 jam, sekali pakai) dan admin bisa membuat tautan yang sama dari `/admin/staff`. Aksi sensitif (undang co-owner, pindah kepemilikan) meminta kata sandi lagi (`lib/auth/reauth.ts`). Pemindahan pemilik utama ada di `/admin/club/owners` (`transfer_ownership`, tercatat di audit). Akun apa pun bisa membuat organisasi sendiri dari `/`. Ekspor data organisasi: `/admin/club/export` (ZIP berisi CSV, daftar tabel di `lib/export/organization.ts`; tabel baru ber-`club_id` harus ditambahkan, kolom rahasia masuk `HIDDEN`). Keanggotaan organisasi ada di `organization_users` (dulu `org_owners`; `base_role` `p_owner`/`owner`/`staff`, tepat satu `p_owner` per organisasi, staf dibatasi `organization_user_clubs`, kosong = tanpa klub); satu akun boleh jadi pemilik beberapa organisasi. - Booking kelas lewat RPC `book_class` (trigger `enforce_booking_rules`): `BK001` kelas sudah mulai, `BK002` tanpa paket aktif di tanggal kelas; hanya admin yang boleh melewatinya dengan `p_late_attendance` (tercatat di log audit). Insert tanpa JWT (seed/service role) tidak dicek.
- Batas data: nama 200, teks bebas 2.000, tanggal lahir 1900..hari ini (WIB), promo berakhir >= mulai, periode gaji per pelatih tidak tumpang tindih; zod (`lib/validations/limits.ts`) dan `CHECK` di database harus sama.
- Idempotensi: pesanan kasir lewat `create_order_once`, pembayaran lewat `add_order_payment_once`, penyesuaian buku kas dengan `client_request_id`; klien mengirim `requestId` (UUID per form, diganti setelah sukses, `RequestIdInput`), kirim ulang dengan ID sama tidak membuat baris baru. Tombol `ActionSubmitButton` terkunci selama form memproses.
- Akun pribadi (tanpa organisasi): login selalu membuka sesi `personal` (`/`, Beranda); klub dibuka lewat "Masuk" di Beranda (`switchContext`), kecuali undangan baru (`resolveClubTarget`). `/signup/account` hanya membuat `accounts` dan sesi `personal`; email unik, tanpa verifikasi. Data pribadi (`workout_logs`, `workout_goals`) tidak punya `club_id`; RLS lewat `current_account_id()` (klaim `account_id`, akun aktif, sesi belum dicabut). Teman dan feed (`friendships`, `posts`, `post_comments`, `post_reactions`, `blocks`, `reports`): hanya teman yang saling melihat; tabel pertemanan hanya ditulis lewat RPC; akun lain dicari dengan username persis. Gabung klub: akun dewasa mengirim `club_join_requests` dengan kode klub (`clubs.slug`); admin dengan `members.create` menyetujui lewat aksi server (`decide_club_join`, service role). Grup dan event (`groups`, `group_members`, `events`, `event_rsvps`): privat, hanya lewat RPC, undangan hanya ke teman. Laporan ditinjau superadmin di `/superadmin/reports` (pemilik atau staf klub hanya kehilangan fitur sosial lewat `accounts.social_banned_at`; email notifikasi laporan baru lewat `REPORT_NOTIFY_EMAIL`); kode klub bisa diganti admin (`rotate_club_code`); username dibatasi sekali per 30 hari; akun pribadi punya ekspor dan hapus akun di `/settings`. Rencana: `progress/social-free-progress.md`; hal yang perlu perhatian pemilik: `progress/social-free-attention.md`. Peringkat grup dan klub membaca `workout_logs` hanya lewat fungsi SQL (`group_leaderboard`, `club_leaderboard`: top 10, hanya yang punya sesi, total saja); papan klub hanya memuat anggota yang opt-in per klub (`club_leaderboard_optins`, bawaan mati, hilang saat keluar klub); kudos = `post_reactions` yang dibaca lewat `kudos_for_posts` (nama hanya untuk teman dan sesama grup). Tabel `club_leaderboard_optins` sengaja tanpa penjaga `a00_org_writable` pada delete supaya persetujuan selalu bisa dicabut.
- Foto dan reaksi (migrasi 064): foto post di bucket privat `post-media` (`<account>/<post>/<n>.webp`), hanya ditulis service role lewat `lib/media/post-media.ts` (`sharp`: maks 1600 px, webp, metadata dibuang; browser juga mengecilkan dulu supaya muat di batas body Vercel), dibaca lewat URL bertanda tangan untuk baris `post_media` yang lolos `can_see_post`; berkas storage dihapus setelah barisnya terhapus (hapus post, moderasi, hapus akun). `posts.hidden_at` diisi trigger saat 3 laporan terbuka, kosong lagi hanya bila semua laporan diabaikan. `post_reactions.kind` (`kudos`/`fire`/`strong`/`clap`). Kartu bagikan `/api/cards/<kind>/<id>` hanya untuk pemilik (data lewat RLS), tanpa nama lengkap.
- Kompetisi (migrasi 063): `club_types.max_m_per_min` (null = tanpa cek, renang 150) ditolak `WL003`; peringkat mengembalikan `prev_rank`, `gap_to_next`, `next_rank`, `prev_champion` (juara periode lalu dihitung saat dibaca, tanpa snapshot); tantangan (`challenges` grup atau klub, `challenge_participants`) hanya ditulis lewat RPC `create_challenge`/`join_challenge`/`leave_challenge`/`delete_challenge`, dibaca lewat `challenge_progress`, kode `CH001`-`CH004`, izin klub `challenges.manage`; lencana `achievements` diisi trigger `award_achievements` setelah insert `workout_logs` (juara bulanan = satu-satunya peringkat 1 sesi bulan lalu di grup dengan minimal 2 anggota, diberikan saat latihan pertama bulan ini); rekor pribadi dan streak dihitung di `lib/data/workouts.ts` (aturan streak sama dengan `workout_streak` di SQL).

## Pelajaran dari pengerjaan fitur sosial (jangan diulang)

Format: kesalahan, lalu langkah yang berlaku sejak sekarang.

Klaim dan catatan
- Menyatakan fakta dari ingatan atau dari catatan lama tanpa memeriksa kode (misalnya "username tidak bisa diubah", "CSP belum membatasi script"). Keduanya salah. Langkah: sebelum menulis sebuah fakta ke daftar atau ringkasan, grep kodenya; catatan tim lama dianggap belum tentu benar sampai dicek.
- Menyimpulkan "lulus" dari output kosong atau dari `| tail`. Langkah: jalankan tes dengan `-v ON_ERROR_STOP=1`, baca kode keluarnya, dan sebut tes mana yang dijalankan; output kosong bukan bukti.
- Menemukan terlambat bahwa fitur baru tidak terjangkau dari jalur login sebagian peran (konteks personal vs klub). Langkah: saat menambah konteks atau halaman baru, tuliskan di awal bagaimana tiap peran sampai ke sana.

Lingkungan uji lokal
- `pkill -f` atau `pgrep -f` dengan pola yang cocok dengan baris perintah shell sendiri mematikan shell sesi (kode keluar 144). Langkah: matikan proses dengan PID atau `pgrep -x`, jangan dengan `-f` yang memuat kata yang juga ada di perintah.
- Proxy atau Next mati diam-diam, lalu kegagalan terlihat seperti bug kode (pembatas laju gagal tertutup sehingga semua pendaftaran ditolak). Langkah: sebelum e2e, cek `curl` ke Next, ke proxy, dan ke PostgREST; jika ada 429 atau 503 yang aneh, curigai layanan dulu.
- Memindahkan PostgREST ke database lain atau membangun ulang skema tanpa memuat ulang cache skema. Langkah: setelah membangun ulang, kirim `kill -USR1` ke PostgREST dan tunggu respons 200.
- Menulis SQL berisi `$` (hash bcrypt) lewat `psql -c` di dalam tanda kutip shell; hash rusak (panjang 54, bukan 60). Langkah: kirim SQL lewat stdin (`input:`) atau parameter, lalu cek panjang hash.
- Menjalankan seluruh rangkaian tes SQL di database yang sudah berisi data e2e, sehingga asersi yang menghitung seluruh tabel gagal. Langkah: jalankan rangkaian tes di database yang baru dibangun; pakai database terpisah untuk e2e.

Tes dan alat uji (bukan bug produk, tetapi sempat dibaca sebagai bug)
- `innerText` Playwright mengikuti CSS `uppercase`; pencocokan teks judul gagal. Langkah: cocokkan tanpa membedakan huruf besar kecil.
- Selektor teks yang juga cocok dengan judul dialog tersembunyi. Langkah: batasi ke `dialog[open]` atau ke kelas elemen yang dituju.
- Username dan nilai lain dibuat otomatis sehingga tes memakai nilai yang salah. Langkah: baca nilainya dari database sebelum dipakai di tes.
- Formulir aksi server dikosongkan setelah kiriman gagal sehingga tes dan pengguna kehilangan isian. Langkah: pakai `ActionForm` (menahan reset saat galat); tes yang mengirim ulang tetap mengisi ulang semua kolom.
- Asersi di bawah peran `authenticated` membaca baris yang disembunyikan RLS atau tabel yang ditutup. Langkah: baca di luar peran itu atau ubah asersinya.
- Menggunakan akun uji yang sama dua kali, atau menghapus akun yang masih punya profil klub (kunci asing menahan). Langkah: pakai surel unik per uji atau bangun ulang database.

SQL dan migrasi
- Mengacu `new.kolom` milik tabel lain dalam cabang yang "tidak jalan" dalam satu fungsi trigger bersama; plpgsql tetap gagal. Langkah: pecah menjadi cabang `if` terpisah per tabel atau fungsi terpisah.
- Memanggil operasi sistem (membuat profil anggota) dari fungsi `security definer` yang berjalan dengan JWT pengguna, sehingga trigger yang membaca `auth.uid()` menolaknya. Langkah: operasi seperti itu dibuat RPC khusus service role dengan izin diperiksa di aksi server (pola `activate_member_account`, `decide_club_join`).
- Memilih izin untuk membatasi akses tanpa melihat preset peran (pelatih ternyata punya `members.portal`). Langkah: sebelum memakai kode izin sebagai pagar, cek `role_permissions` tiap preset.
- Lupa bahwa tes isolasi akun (`accounts_phase1`) dan tes jumlah tabel berskala klub (`seats_phase4`) menghitung semua objek baru. Langkah: setiap tabel atau view baru dicek terhadap keduanya, dan pengecualian ditulis di tes.
- Tabel baru tanpa pembatasan kolom insert untuk peran klien. Langkah: untuk tabel yang diisi pengguna tetapi memuat kolom moderasi atau status, beri `grant insert (kolom...)` hanya pada kolom yang boleh diisi.
- Setelah `apply_migration` ke hosted, versi di `supabase_migrations.schema_migrations` memakai cap waktu. Langkah: ganti versinya dengan nomor berkas, lalu tampilkan daftar versi untuk memastikan.

Kode
- Memanggil fungsi tak murni (`Date.now()`) di komponen server memicu galat lint kemurnian. Langkah: hitung nilai itu di lapisan data.
- Mengubah `ActionForm` (dipakai di seluruh aplikasi) tanpa menjalankan alur yang sudah ada. Langkah: setelah mengubah komponen bersama, jalankan ulang satu e2e yang memakai alur sukses dan alur gagal.
- Uji migrasi ke hosted sebelum diterapkan (dry run): `supabase db push --dry-run` butuh token akses dan kata sandi database yang tidak ada di lingkungan ini. Gantinya, jalankan isi berkas migrasi di dalam `begin; ... select <pemeriksaan>; rollback;` lewat `execute_sql` pada project hosted, lalu cek bahwa tabel atau kolom baru tidak ada setelahnya. Kegagalan di tengah juga tidak menyisakan perubahan. Setelah lulus, `apply_migration` dan ganti versinya ke nomor berkas. Pemeriksaan yang pernah menyelamatkan: constraint lama di tabel yang diubah.
